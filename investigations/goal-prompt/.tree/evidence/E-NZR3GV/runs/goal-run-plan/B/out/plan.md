# Plan for the G-D1CH1R goal run (answers from the prompt and skills only)

Sources: `prompt.txt` (the /goal prompt), `skills/hyp-goal-run/SKILL.md`, and the two skills it names, `skills/hyp-prototype/SKILL.md` and `skills/hyp-verification/SKILL.md`.

1. **Naming and tying candidates; what a fix is.** Candidates are Hypotheses (`H-` ids) that are rival siblings under a top-level Question. Give each one a short name with `--alias` when it is added, and use the alias anywhere. Tie each candidate's subject before the run that tests it with `hyp subject <H> [PATH…] --base <commit> [--patch FILE]`, because a Result covers a candidate only when it gave that candidate a verdict or when its whole subject (base, patch and files) is held by one of the Result's cited runs. A fix is never an edit to an existing node. It is a new Hypothesis added with `hyp add hyp --parent <Q-id>`, then `hyp supersede <new H-id> --old <old H-id>`, then `hyp add exp --parent <new H-id>`, in that order, and it exists before the Experiment that tests it. The skills do not give a naming convention for candidate commits.

2. **Verdict rules: what each holds and when I write it.** Each Experiment's verdict rule is pinned when it is added: `hyp add exp ... --rubric <name@version>` for a rubric in `rubrics/`, or `--rubric reading` with the rule written in the Experiment body. I write the rule before any candidate is run, and I run no candidate until the rule is recorded on the Experiment. A recipe's checks may exist before that, since `hyp add exp` pins them. A new or changed check is tried only on its cases' stand-ins until the rule is recorded. A failed pre-registered pass rule is `contradicts`. `inconclusive` means the Experiment ran as designed and still could not decide. When a verdict rests on my reading of a Goal line, I write the other reading as a separate strict check with its own known answers. That check sets no verdict. It is named in the rule, run on the same candidates, and recorded with `hyp record --reading`. Where Results are reassessed under an owner answer, the rubric changes only as a new version, and `--rubric reading` carries the rule in its body. An outcome that is already known is stated in the rule.

3. **Where logs are kept.** Hand-gathered evidence goes in `.tree/evidence/<E-id>/` under the store, with short file names: command output, logs, timings and `git rev-parse HEAD`. It is saved while the sandbox still exists, before Cleanup. Scripted Evidence from a recipe is written with `hyp bundle evidence --record .tree/evidence/<E-id>/<name> REF OUT_DIR`. A Result cites only files of its own Experiment's run, plus any records pinned with `--records`. A longer observation goes in an evidence file, not in `--observation` (600 characters) or `--why` (300 characters). A runner checkpoint is recorded with `hyp checkpoint`, not kept in chat. The skills name no other log location.

4. **What I do before the stop about a review, and how findings are sorted.** The skills describe no review step before the stop. The only step before the last message is recording the runner checkpoint: `hyp checkpoint --summary "Stopped: <stop clause>. Waiting for the owner: <keys under AWAITING OWNER>. Out-of-Goal findings: <one short phrase each, or none>" --why "<why>"`. Findings are sorted this way. A finding that is a case of one of the Goal's lines gets a limit, a refer or a reading, as the skills describe. An out-of-Goal finding, which is a case of none of the Goal's lines, gets no limit, no refer and no reading. It is named in the checkpoint, and it never holds the select. A defect in text I changed and may edit is fixed with a commit before the stop.

5. **What my last message lists for the owner.** The last message repeats the runner checkpoint. It lists each line under LINES by its key, with the Results that ran it. It names each Question where OWED still owes a line, and it lists the keys under AWAITING OWNER with the owner's exact question for each reading (`hyp show <Q-id>` and the rivals' `hyp show` output). It names the out-of-Goal findings. A run that ends with lines owed is a normal result, and I print `hyp status G-D1CH1R` at the end of the turn. The stop clauses from the prompt are: OWED reads "runner owes nothing: stop and report to the owner", or 5 Results are recorded under claude-g1b-6, or I cannot take the next step honestly and I say why. Stopping is not success.
