# Spec: events, refusals and replay rules

This file is the single authority for the event schema, the refusals and the derived-status rules of `hyp`; [sandbox-spec.md](sandbox-spec.md) owns the sandbox. Plans, skills and Go comments point here instead of restating the rules; Go comments cite it by section as "spec §N".

Keeping it current:
- A change to an event type, a refusal or a derived rule updates this file in the same PR.
- Section and rule numbers are cited from code, so never renumber them: add a new refusal at the end of §5's list and a new rule under the section it belongs to.
- If code and this file disagree, treat it as a bug. Decide which one is wrong, fix it, and say which in the PR.
- Text marked **[not built: #N]** is decided but not built yet. It states the target, so it is not a disagreement under the rule above. The PR that builds it removes the mark, and issue #N tracks what is left.

This spec adds the minimum needed to make the owner-confirmed design executable; additions are marked **[added]** with the reason.

## 1. Names and locations

- Binary: `hyp` (the word `tree` is aliased in the owner's shell and collides with the common `tree` utility). "tree" stays the concept name.
- Store directory in the investigated repo: `.tree/`, found by walking up from the current directory. The walk stops at the repository root, the first directory that holds `.git` (a directory, or a file in a worktree): when no directory from the current one up to that one is a store of the record (§1.1) or holds `.tree/events` in the work tree, a command reports `no .tree store found` (exit 3), even when a directory above the root holds a store. With no `.git` at or above, the walk goes to the filesystem root (ADR 0022). A store's name is its folder's path from the repository root, `.` for the root.
- `hyp init` refuses, at exit 1, a directory from which this walk finds a store, at it or above it, names that store's directory and creates nothing; a store is made only where no command would read another one. In a git repository it also starts the record (§1.1), unless the clone is a sandbox clone.
  - `.tree/events/<actor>.jsonl`: append-only, in any line order (§6). In a record repository the record holds it; elsewhere it is git-tracked in the work tree.
  - `.tree/.gitattributes` contains exactly `events/*.jsonl merge=union`, which `hyp init` writes: `git merge` of two branches that each appended to one work-tree events file keeps every line of both once, with no conflict.
  - hyp keeps no index; every read replays the events (ADR 0006). Older hyp binaries write `.tree/index.sqlite`, so the `.gitignore` below still names it; hyp neither reads nor deletes one.
  - `.tree/evidence/<experiment-display-id>/`: evidence files referenced by pointer. A Result stores each file pointer's sha256 (`evidence_sha256`).
  - `.tree/.gitignore` contains exactly `index.sqlite`, `index.sqlite-*` and `evidence/`: git ignores every evidence file, since the record keeps each file an event names (ADR 0024). `hyp import` adds the `evidence/` line to an older store's `.gitignore`.
- Recipes: `recipes/<name>@<version>/`, in the directory that contains `.tree/` or in any parent up to the repository root (the first directory holding `.git`). See `skills/hyp-verification/RECIPE-FORMAT.md`. [sandbox-spec.md](sandbox-spec.md) §1 says when hyp runs a recipe's commands and whether a sandbox exists then.
- Rubrics: `rubrics/<name>@<version>/`, looked up the same way. A rubric is a bundle in the recipe format with no step section and one Standalone command (§7.6); recipes and rubrics are the two kinds of bundle, and `hyp bundle` replaces `hyp recipe` for both, which stays a hidden alias (ADR 0018); a name is used in one library only, and `hyp check` names one used in both.
- Actor: the `--actor` flag, or the `HYP_ACTOR` environment variable. It must match `^[a-z0-9][a-z0-9-]{0,39}$`. If it is missing, every write command fails with exit 2. There is no default actor.

### 1.1 The record (ADR 0024)

A record repository is a git repository that holds the hidden ref `refs/hyp/record`. Its record is every event of every store of the repository, the bytes of every file an event names, the files of each bundle an event pins, and every commit a Hypothesis subject names. Package `record` alone reads and writes it.

- **Stored.** Commits on `refs/hyp/record`, which no branch holds. A commit's tree holds each file at its path from the repository root: `<store>/.tree/events/<actor>.jsonl`, each named file at `<store>/<path the event holds>`, and each pinned bundle's hashed files at the bundle's path. A commit's first parent is the record before it; each later parent is a subject commit, so it stays reachable. The record holds no other file but the kept copies a `hyp sync` join writes under `<store>/.tree/kept/<sha256>`, each the bytes of a named file whose path the record holds with other bytes. A store enters the record with its first event.
- **Derived.** A snapshot: the files of one record commit written once under the common git directory (`hyp/snap/`), as hard links to a blob cache, which every read of a store reads below. A commit never changes, so neither does its snapshot; a snapshot no read used for an hour is removed. A worktree act (checkout, reset, clean, branch deletion, worktree removal) touches neither the ref nor a snapshot.
- **Which store folder a command uses.** In a record repository, the record's copy of the store when the record holds it, else the work-tree folder (see the refusal below). In a sandbox clone, which `hyp sandbox create` marks in the clone's common git directory, a git repository with no record ref, a `.git` that git cannot open, no git on `PATH`, and a directory with no `.git` at or above it, hyp reads and writes the work-tree `.tree/` as before the record.
- **A write's steps.** Take the clone's one write lock (`hyp/record.lock` in the common git directory), so writes from every worktree take turns, and reread the ref. Replay and validate as §5. Then write the objects (the events file with the new line, each named file), the tree, the commit, and last move the ref with a compare-and-swap from the commit read under the lock. The write exits 0 once the ref moved. A write stopped before that step leaves the record as it was; its objects are unreferenced and `git gc` may prune them. No read sees part of a write.
- **Refusals (exit 1).** A write in a folder where discovery finds a work-tree `.tree/` that holds an event whose id the record lacks, naming `hyp import`; a write naming a file whose path the record holds with other bytes, since a named file never changes; a named file in neither the work tree nor the record; `hyp import` and `hyp sync` in a sandbox clone. `hyp import` of a folder that holds no store, or a REF that names no commit, is exit 2. `hyp sync` against a remote that cannot be read or refuses the ref is exit 3.
- **`hyp sync [REMOTE]`** (origin by default) fetches REMOTE's `refs/hyp/record`, joins the two records and pushes the join. When one record is an ancestor of the other, the join is the later one. Otherwise it is a commit with both as parents whose tree holds every path of both: an events file both changed keeps each id once, the local line when both hold it, every line in id order; any other path both hold with other bytes keeps the local copy at that path and the remote's copy under its sha256 in the kept folder of the store that holds the path (`.tree/kept/<sha256>`), and prints a warning, so each event still finds the bytes it names. A remote with no record gets the local one.
- **`hyp import [REF:]PATH...`** adds, in one write per store, every event of the work-tree store at PATH, read from the checkout or from commit REF, whose id the record's store lacks, with the bytes of each file those events name, each bundle they pin whose source copy hashes as pinned, and their subject commits; it prints each named file or bundle it could not find. Run again, it adds nothing. For a store read from the checkout it then adds `evidence/` to the store's `.gitignore` and untracks each file under `.tree/evidence/` that no event of the record's store names, leaving it on disk.
- **`hyp show FILE[@SHA256]`** prints the bytes of a file an applied event names, from the record's copy in a record repository. Every read of a named file reads the bytes with the sha256 its event stores: the kept copy when the record keeps one, the file at its path otherwise. When events name FILE with more than one content, `hyp show FILE` exits 2 and names each as `FILE@<sha256 prefix>`, and `FILE@<prefix>` picks one.
- A write that names a file reads its bytes once, under the write lock: it refuses bytes whose sha256 differs from the one the event stores (the file changed while hyp wrote it), and keeps the bytes it hashed.
- **`hyp check`** in a record repository also warns when the work-tree store holds events the record lacks, and for each checked-out bundle whose hash differs from a pin of the same ref.
- **A merged log.** Two records join only through `hyp sync`, as a set by event id; replay orders the joined events by §6 as for any merged log.

## 2. Ids

- Every event has `id`, a ULID (26 characters, Crockford base32, upper case), generated monotonic per process. An appended event's id sorts after every event id the store holds: when the clock reads earlier than the newest id, or in its millisecond, the new id takes the millisecond after the newest id's, with fresh random bits, so two clones whose clocks are behind append different ids. In the greatest ULID millisecond it adds one plus a random 32-bit amount to the newest id's random bits, or one when that overflows, an id two clones may then share. The newest id is the greatest id of the form above; a line whose id has another form is rejected by replay (§5) and does not count. When no ULID sorts after the newest id, because it is the greatest ULID or an id of that form above it, the append is refused (exit 1) and writes nothing (ADR 0022). `ts` keeps the clock's time.
- `node.add` and `result.record` create a node whose node id equals the event id.
- Display id: `<K>-<last 6 characters of the ULID>`, where K is `G` (Goal), `Q` (DesignQuestion), `H` (Hypothesis), `E` (Experiment) or `R` (Result). Example: `H-7QK2ZD`.
- Optional alias on `node.add`: it must match `^[a-z][a-z0-9-]{0,31}$` and be unique in the log.
- Resolving a user-typed reference, in order: an exact ULID, then an alias, then a display id. Zero matches gives `unknown node <ref>`. Two or more matches gives `ambiguous node <ref>`. Both exit 2, because the fix is in the command line.

## 3. Event envelope

One JSON object per line:

```json
{"v":1,"id":"01JB...","ts":"2026-10-24T03:00:00.123456789Z","actor":"claude-a","type":"node.add","node":"01JB...","payload":{...},"why":"..."}
```

- `v` must equal `1`. `ts` must be RFC3339Nano in UTC (ends in `Z`).
- `why` is required on every event but `answer`: 1–300 characters, counted in runes (`utf8.RuneCountInString`), never bytes. `node` is required on every event but `answer`. An `answer` is the owner's act: it has no `node` and no `why`, and its `node` and `why` are `""`; the owner's reason is each item's text (§4, ADR 0020).
- hyp appends each event as one line, in one write to the actor's file opened for append, and syncs the file before it reports the event written. A crash during the write can leave a last line cut short; it does not parse, so replay skips it and reports it (§6), and the store holds every event before it whole.

## 4. Event types (closed set)

|---|---|---|

**[added] `dq.resume`**: undoes a defer or withdraw. Without it a mistaken defer is permanent in an append-only log.
**[added, then removed from use] `confirm` with `role`**: §3 required a verifier check on every select and an owner check on trade-offs, and replay can only be pure if both are stored events. The verifier role is retired (ADR 0015), and the owner confirm with it (ADR 0019): the select is the gate, and a scope change is a Goal line the owner accepts, or a new tree. `hyp confirm` exits 2. Old logs keep their confirms, and only an owner confirm's `accepts` applies.
**[added, then removed from use] `dq.request_verify`**: asked the verifier to judge the current select again. No command writes this event (ADR 0011, ADR 0015). Old logs keep it.
**[added] `experiment.withdraw`**: closes an Experiment that will not run and that no other Experiment replaces; one that is replaced gets a `supersedes` edge from its replacement instead (ADR 0008). Without either, an Experiment that will never run stays `planned`.
**[added] `hypothesis.amend`**: replaces a Hypothesis body. Without it a wrong body can only be fixed by superseding the Hypothesis.
**[added] limits**: a Result names the limits it found (`limits`): each is a case the Goal covers that no check ran on the Hypotheses the Result judged (ADR 0016). A later Result that runs the case closes it (`closes`). A limit's key is `<result-id>#<n>`: the Result's full ULID, then `n`, which counts the Result's `limits` from 1. The CLI accepts any node reference before the `#` (§2) and stores the full id. An owner checkpoint accepts a limit the runner referred (`accepts`); an old owner confirm's `accepts` is replayed as an accept. §8 derives each limit's state, and §8.2 states which move applies from which state. `hyp record` prints the key of each limit and reading it records, under the Result's line, so a later command names them without counting `--limit` or `--reading` flags, and the whole text of each limit it closes (`  closes R-…#n: <text>`). A close covers every case its limit names; a case the Result did not run is a new `--limit` on it, referred when void (ADR 0016). A close records that the case ran, whatever the verdicts: a Result that runs the case and contradicts a Hypothesis closes it too. `hyp record` warns, at exit 0, when its Experiment aims at an open limit that the Result neither closes nor follows with a new `--limit` (`warn: E-… aims at R-…#n and this Result does not close it; …`), since an instrument failure may leave an aimed limit open on purpose.

**[added] pre-registration**: an Experiment is a pre-registered Result (ADR 0018). It binds a Recipe and a Rubric to the tree, and before the run it fixes five facts that never change after the add: its **targets**, its `aims`, its recipe (`recipe` and `recipe_hash`, or `none`), its rubric (`rubric` and `rubric_hash`, `reading`, or none) and its `records`. A different recipe or rubric is a new Experiment. The targets of an Experiment under a Hypothesis are that parent and each Hypothesis in `targets`; an Experiment under a DesignQuestion has none. Every Result gives a verdict on each target and on nothing else (§5 rule 6), so a Result under an Experiment with no targets has no verdicts and carries its measures in its observation and its cited records. The **shape** is derived from the parent kind, the targets and the rubric, and no field stores it:

| Shape | Parent | Recipe | Rubric | Records |
|---|---|---|---|---|
| run and rule | Hypothesis | pinned | bundle | its own run |
| rule by reading | Hypothesis | pinned or `none` | `reading` | own run or pinned |
| reassess from kept records | Hypothesis | `none` | bundle or `reading` | pinned |
| measure only | DesignQuestion | pinned | none | its own run |

It is read in this order: under a DesignQuestion, measure only; with a rubric bundle, run and rule when the recipe is pinned and reassess when it is `none`; with `reading`, reassess when the recipe is `none` and `records` is not empty, and rule by reading otherwise. An Experiment with no rubric, written before #106 or merged in, reads as run and rule when its recipe is pinned and as rule by reading when it is `none`. `hyp add exp` refuses a rubric bundle with recipe `none` and no `records`, since the rubric would have no measures to read (§5.1). `hyp show E` prints the shape. A record is a file under `.tree/evidence/`; the Experiment's own run is `.tree/evidence/<its display id>/`. `records` pins earlier records the way a Hypothesis's subject pins files: a directory given at add stands for each regular file under it, `path` is relative to the store root and is a pointer, and the sha256 is the identity. A record is never named by a Result id, because a ruling depends on the bytes, not on another Result's claim.

**One field, one transition.** A payload field that names keyed items names one kind of item and one transition. A Result's `closes` closes limits; an answer's `answers` answers readings, its `accepts` accepts limits and its `returns` returns them; a checkpoint's `refers` refers limits; a Goal add's `lines` writes the Goal's lines; an old checkpoint's `closes`, `revises`, `accepts`, `returns` and `lines` are history; `aims` names intent and settles nothing (ADR 0013). A confirm's `accepts` is history (§8.2).

**[added] lines**: the Goal's lines are the cases every candidate must meet (ADR 0016 amendment "a Goal line is a limit the owner records"). They come with the Goal: the owner adds the Goal with `lines` on its `node.add` (`hyp add goal --line TEXT`, repeatable), and no later event adds a line (ADR 0020). A line is never edited: what it means is a reading, a line the Goal no longer needs is referred and accepted, a case under it is a limit the owner returns, and a new line is a new Goal, which may sit in the same store. A line is a limit keyed on the Goal, `<goal-id>#<n>`, where `n` counts the add's `lines` from 1, and it has every move a limit has: a Result `closes` it, an Experiment `aims` at it, a checkpoint `refers` it and an answer `returns` or `accepts` it. Its scope is the Goal, so a Result under any question may close it and an Experiment under any question may aim at it. `hyp add goal` prints the key of each line it writes (`  line G-…#n: <text>`). `hyp add goal` refuses with exit 1 a line that names a run of 8 to 63 hex digits followed by an ellipsis (`…` or `...`), a hash cut short, naming the rule: a line never changes, so a hash it names is whole (64 hex digits for a sha256). Only the write refuses, so a log that already holds such a line still replays. An old Goal's lines were written on its first owner checkpoint (`hyp checkpoint --role owner --line`, no longer a command); replay still applies them, with the same keys, and that checkpoint counts as the one write. **Cites**: a line names 0 to 10 plain keys (`hyp add goal --cite N=KEY`, repeatable), each settled when the line is written: a line, an accepted or closed limit, an answered reading, or a selected or contradicted Hypothesis (by its id). Anything else is refused at exit 1 (§5 rule 31). A cite carries no relation label: what it means is derived from the key's state at the line's place in the log, a line or an accepted limit **carried**, a closed limit or a contradicted Hypothesis **forbidden**, an answered reading **applied**, a selected Hypothesis **realised**. A Goal's origin is the Goals its cited keys belong to. When a cited key's state later differs, `hyp check` warns (`warn: G-…#n cites H-…, which was realised when the line was written and is unsettled now`) and `hyp show G-…#n` prints both (`cites H-…: realised, now unsettled`); no status changes. A Goal of a store with many Goals is named on a checkpoint with `hyp checkpoint --goal G-…` (without it, exit 2).

**[added] subject**: a subject has one shape, a base commit plus what is given over it: at most one patch, and input files (ADR 0020). A Hypothesis may name its subject, what embodies its claim, with `hypothesis.subject` (`hyp subject H [PATH…] [--base COMMIT [--patch FILE]]`, or `hyp add hyp --subject PATH`, which writes the add and the tie). Over a base, `--patch` names the one patch applied over it, and the PATHs are the input files given to the code; `--patch` without `--base` exits 2. `--base` is resolved in the git repository that holds the store root to a full commit id (exit 2 when it names no commit, exit 3 when `git` is not on PATH). A directory stands for each regular file under it. `path` is relative to the store root and is a pointer for readers; the sha256 is the identity. A Result keeps one subject per cited run, `subjects`, and a run's subject **holds** a Hypothesis's subject (`replay.HoldsSubject`) when, if the Hypothesis names a base, the run is at that base with the same patch, none when the Hypothesis names none, and was given each of the Hypothesis's files as an input file, compared by sha256. A patch changes the code and an input file is data given to the code (owner answer to R-0HABWN#7 in checkpoint-store), so a run at B plus a patch never holds bare B, a run at bare B never holds B plus a patch, and a run at B given input files holds bare B. If the Hypothesis names no base, as every subject before ADR 0020, the run holds it at any base when it was given each of its files, as its patch or as an input. An old Result's `fingerprints` read as one subject with no base, so the coverage they gave is unchanged. The latest tie stands until a run subject of a non-retracted Result holds it; after that the bytes ran as this Hypothesis, and a different subject is a different Hypothesis, added and superseding it. Two Hypotheses may share a subject, since the claim is what differs. A tie is a claim hyp cannot check: that these bytes embody the words. `hyp record` reads each cited `command.json` and `sandbox.json` under the store and writes one subject for each, in evidence order, keeping one of two that are alike: a command record's has no base and no patch, and the sha256 of each input and each directory entry (format 6) as its files; a sandbox record holds one run per Arm, each at its base with that Arm's one patch as its `patch` and the inputs file as its files, and with no Arm one run at its base given the inputs file; an Arm whose patch is not named by a lowercase hex sha256 gives no subject, since the code it ran is unknown. It copies them as it copies `evidence_hashes`; replay reads no files, so the log must hold them for coverage (§8) to reach the ledger.

**[added] readings**: a Result names a line of the Goal that a verdict rests on and how the run read it (`readings`). A reading's key is `<result-id>#r<n>`, and `n` counts the Result's `readings` from 1. Its states are open and closed, and both are derived. An owner answer closes it: its `answers` names the key, and the item's text is the owner's answer, which `hyp show` prints beside the closed reading (an old owner checkpoint closed it with `closes` and its `summary`). An owner changes an answer they gave with a later answer that names the key again: whether an item is a first answer or a revision is derived from the reading's state, so the old `closes` and `revises` merge (ADR 0020). `hyp answer` warns, at exit 0, when it revises a key that a line of another Goal cites. The answers are kept in merge order, the close first, and the latest is the answer in force; `hyp show` prints it beside the reading and each earlier one beneath, with the Result that applied it. A revision never reopens the reading and changes no event before it: an earlier Result keeps its verdicts, and a Hypothesis it contradicted stays contradicted until a new Result judges a successor. In an old log, a `revises` that sorts before its key's close is refused, and a second `closes` of an answered reading is rejected; two revisions both apply, the later in force. A reading of a retracted Result is left out. It refuses, at exit 1, a key that names no reading, a retracted Result, and an answer under the actor that recorded the Result. An open reading prints under AWAITING OWNER and changes no status: it never changes a question's state or the Goal's. It holds back ledger items on its question only while its **reach** is not empty: the live Hypotheses under that question whose standing the answer can move, read from the Result's own verdicts, which are a candidate the Result judged, and a contradicted rival whose only `contradicts` is that Result's. While the reach is not empty it holds `rivals`, `select` and `choose`, because the answer may revive a rival, drop the lone candidate or change the candidates (§8.1). A reading whose reach is empty, such as one whose Result's Hypotheses another Result has since contradicted, holds nothing. A closed reading is **applied** by the first non-retracted Result that lists its key in `applies`. Each answer is applied by the first non-retracted Result after its checkpoint, and before the next revision, that lists the key in `applies`, and by no other Result: a later Result under the question may have run for another reason, such as a repair, and never read the answer (ADR 0013 amendment of 2026-11-09). A tree written before `applies` existed therefore owes `reading` for answers its Results applied without naming them. The reading is applied when the answer in force is. Until a Result applies it, an answered reading is the runner's `reading` item (§8.1), which holds back the owner's `choose` on its question, because the owner's answer cannot yet have changed the candidates. Closing one does not change the Goal's text. A reading reads either a line of the Goal or an owner's answer to an earlier reading; a reading of an answer names that reading's key in `of`. It narrows the answer and never reopens it: the earlier reading stays closed and its answer stays in force, and the owner changes their words only by a rule change. `of` may name only a closed reading of a non-retracted Result, so a chain always points back in merge order and holds no cycle; a merged log in which the reading of an answer comes before its close rejects that Result. Without this, a verdict's reliance on an unclear Goal line stays in prose the owner has to go looking for. Two readings with the same `of` and the same text, spaces trimmed, **ask the same question**: each holds its own Result's question, and nothing stored ties them. `hyp status` prints the open ones as one AWAITING OWNER line, each key with its question, and `hyp answer` warns (`warn: R-…#r1 asks the same as R-…#r1 and stays open; add --answer R-…#r1`, or `… keeps its earlier answer; add --answer …`) when it leaves a copy behind (ADR 0013).

Content limits, in runes: `title` ≤ 200 and non-empty; a Hypothesis's `body`, an amend's `body` (also non-empty) and `observation` ≤ 600; an Experiment's and a DesignQuestion's `body` ≤ 2000, because it holds a rubric decided by reading or a difference test; a runner checkpoint's `summary` ≤ 2000, because it holds a stop report; a Goal's `body` ≤ 3000, because it holds the owner's met rule and constraints; a records path ≤ 300; each field holds its whole text in its event, `hyp show` prints it whole, and `hyp status` prints the last checkpoint's `summary` whole; a checkpoint `summary` prints on one line in both, each line break as a space; a reading ≤ 600, because it holds both meanings of a Goal line and the question for the owner; `why` 1–300.

## 5. Refusals

The same function, `replay.Validate(state, event) error`, is used by the CLI before appending and by replay on every event. At replay time a refused event is **skipped and reported** as a `Rejection{EventID, Reason}`; replay never panics and never stops on a bad event. This covers logs merged from several worktrees, where each event was valid alone.

Each event type's rule is its entry in the table in `internal/replay/rules.go`, with its apply and basis nodes (ADR 0013). A rule takes `Facts`, so it cannot read a derived status.

An event is refused when any of these holds:

1. `v` ≠ 1, the type is unknown, a required field is missing, `id` is not 26 characters of upper-case Crockford base32 (§2 says what an append does after an id of that form above the greatest ULID), an unknown payload field is present, `ts` is not UTC, or a content limit is exceeded.
2. Its `id` duplicates an earlier event id.
3. `node` or a referenced id (parent, target, hypothesis, select, `to`) does not exist yet, or has the wrong kind.
4. Wrong parent kind. Goal: parent `""`. A store holds many Goals (ADR 0020): a tree is the view of one Goal and every node whose parents lead to it. DesignQuestion: parent is the Goal or a Hypothesis. Hypothesis: parent is a DesignQuestion. Experiment: parent is a Hypothesis, or a DesignQuestion. Result: parent is an Experiment.
5. An Experiment `targets` entry is not a Hypothesis with the same parent DesignQuestion as the Experiment's parent, or equals the Experiment's parent. An Experiment under a DesignQuestion with `targets`, `rubric`, `rubric_hash` or `decided_by` (`bad experiment: an Experiment under a DesignQuestion has no targets and no rubric; it measures`), or with recipe `none` (`bad experiment: an Experiment under a DesignQuestion measures, so it pins a recipe`).
6. A `result.record` verdict key is not one of its Experiment's targets: its parent Hypothesis or one of its `targets`. A `result.record` that leaves a target without a verdict (`bad verdicts: E-… targets H-…; give it a verdict, inconclusive when the run could not decide`), and one with any verdict under an Experiment with no targets (`bad verdicts: E-… has no targets; it measures`). This replaces the `unjudged` mark (ADR 0018).
7. `result.retract` on a Result that is already retracted. `hypothesis.abandon` on a Hypothesis that is already abandoned, or superseded (`bad abandon: <id> is superseded`): superseding already took it out of the live set.
8. `dq.select` of a Hypothesis that is not a direct child of that DQ, or is superseded or abandoned.
9. An owner `confirm` whose `select` is not a `dq.select` on this DQ. A `verifier` confirm is history and is not refused (§4). No command writes a confirm; the rule keeps old logs replaying as they did (ADR 0019).
10. `supersedes` where `from` = `to`, the two Hypotheses have different parent DQs, or the edge would create a supersedes cycle. **[added]** It may also join two Experiments, whose parent Hypotheses must have one parent DQ (`cross-DQ supersedes`); it is refused between an Experiment and any other kind (`wrong kind`), and onto an Experiment that has a non-retracted Result (`bad supersedes: <id> has the non-retracted Result <id>`).
11. `depends_on` whose `from` is not a Hypothesis or DQ, whose `to` is not a Hypothesis, where `from` = `to`, or where the edge would create a cycle among `depends_on` edges, which is the only way the **combined status graph** can hold one (see §7.2).
12. `edge.add` duplicating a live edge; `edge.remove` of an edge that is not live.
13. An `alias` that is already used.
14. `hypothesis.amend` on a Hypothesis that is superseded or abandoned (`bad amend: <id> is superseded or abandoned`), or whose `body` equals the current body (`bad amend: body is unchanged`).
15. A limit key in `closes` or `accepts` that does not name a limit (`bad limit ref`): the key is not `<ref>#<n>` with n ≥ 1; `<ref>` is neither a Result nor the Goal; the Result is retracted; n is greater than the Result's number of limits, or the Goal's number of lines (`bad limit ref: the Goal has N lines`); or the Result is not under the question. For `closes` the question is the one the new Result belongs to (the parent DQ of its Experiment's Hypothesis); for a confirm's `accepts` it is the confirm's DQ. A line is under every question of its own Goal; a close of another Goal's key is refused by rule 32, and an answer's accepts may name keys of several Goals.
16. Removed (ADR 0011). Nothing refuses a `dq.request_verify` beyond the envelope checks in rule 1.
17. An owner `confirm` with `accepts` whose verdict is not `sufficient` (`bad confirm: only a sufficient owner confirm accepts limits`), or that accepts a limit a Result closed (`bad accepts: <key> is closed by R-…; its case ran, so there is nothing to accept`). No command writes a confirm's `accepts` any more; the rule keeps old logs replaying as they did.
18. A `result.record` `evidence_hashes` key that is not an entry of `evidence` or does not clean to `recipes/<name>@<version>/<file>` (`bad evidence_hashes: …`), or a value that is not lowercase hex (`invalid evidence_hashes value for …`).
19. `decided_by` on a node that is not an Experiment (`unknown field`), or a value other than `reading` (`invalid decided_by`).
20. `experiment.withdraw` on a node that is not an Experiment (`wrong kind`), on one already withdrawn (`already withdrawn: <id>`) or superseded (`already superseded: <id>`), or on one that has a non-retracted Result (`bad withdraw: <id> has the non-retracted Result <id>`). `hyp withdraw REF` writes `experiment.withdraw` for an Experiment and `dq.withdraw` for any other node.
21. `aims` on a node that is not an Experiment (`unknown field`); more than 10 (`over limit`); a key named twice, a reading key that names no reading or a retracted Result's reading, a reading still open (`bad aim: reading <key> is open; only an answered reading can be applied`), or a limit key that names no limit under any question (all `bad aim: …`).
22. A `result.record` `closes` key under another question than the Result's, unless its Experiment's `aims` names the key (`bad limit ref`). An `applies` key that is not among its Experiment's `aims` (`bad applies: <key> is not among <exp>'s aims`).
23. A `checkpoint` or `answer` move on a reading or a limit that the move tables of §8.2 refuse. The refusals that name `closes` and `revises` below read old owner checkpoints, which replay still checks as written; an answer's `answers` item is a close of an open reading and a revise of an answered one, so it meets neither the close nor the revise refusal by state. For readings: a `closes` or `revises` without the owner role (`bad checkpoint: only an owner closes a reading`, `… revises an answer`), a limit key (`bad closes: <key> is a limit; an owner accepts a limit with accepts`, `bad revises: <key> is a limit; a limit is closed, accepted or referred, never revised`), a bad key as in §4 readings (`bad reading ref: …`), a close of an answered reading (`bad closes: <key> is answered; an owner revises an answer with revises`), a revise of an open one (`bad revises: <key> is open; an owner answers an open reading with closes`), a key in both `closes` and `revises`, or a move under the actor that recorded the key's Result (separation of duties). For limits and lines: more than 10 keys in a field (`over limit`); a key that names no limit (`bad refers: …`, `bad accepts: …`, `bad returns: …`); an `accepts` or `returns` without the owner role (`bad checkpoint: only an owner accepts a limit`, `… returns a limit`); a `returns` key also in the same checkpoint's `refers` or `accepts`; a `refers` of an accepted limit (`bad refers: <key> is accepted; only the owner reopens it, with returns`); an `accepts` of a limit whose latest hand is not a refer (`bad accepts: <key> is not referred; only a referred limit is accepted, so the runner refers it first`); a `returns` of one whose latest hand is not a refer or an accept (`bad returns: <key> is not referred or accepted; only a referred or accepted limit is returned`); a `refers`, `accepts` or `returns` of a Result's limit that a Result closed (`bad refers: <key> is closed by R-…; its case ran, so there is nothing to refer`, `bad accepts: <key> is closed by R-…; its case ran, so there is nothing to accept`, `bad returns: <key> is closed by R-…`); or an `accepts` or `returns` under the actor of the latest refer (`separation of duties: <actor> referred the limit it accepts`, `… it returns`). `hyp checkpoint` refuses `--role`, `--closes`, `--revises`, `--accept`, `--returns` and `--line` at exit 2, naming `hyp answer` or `hyp add goal --line` (ADR 0020). In a merged log, a return or an accept that sorts before its limit's refer is rejected and reported.
24. A `checkpoint` `lines` without the owner role (`bad checkpoint: only an owner writes the Goal's lines`), when the Goal's add carried lines (`bad lines: a Goal's lines come with its node.add, and G-…'s did; a new line is a new Goal`), when an earlier checkpoint wrote lines (`bad lines: the Goal's lines are written once, by <checkpoint-id>; a new line is a new Goal`); the rule is per Goal, so each Goal of a store has its own first checkpoint with lines, with more than 10 lines (`over limit`), or a line outside 1–300 runes.
25. A reading whose `of` names no reading or a retracted Result's (`bad reading of: …`), or a reading still open (`bad reading of: <key> is open; the owner has not answered it`).
26. A `hypothesis.subject` on a node that is not a Hypothesis (`wrong kind`), on one superseded or abandoned (`bad subject: <id> is superseded or abandoned`), with no base and no files (`bad subject: no base and no files`), a base that is not a full commit id (`bad subject: base "<x>" is not a full commit id`), a patch with no base (`bad subject: a patch with no base`), a patch path outside 1–300 runes, a patch sha256 that is not lowercase hex (`bad subject: patch "<x>" is not a sha256`), more than 50 files (`over limit`), a path outside 1–300 runes or named twice, the patch's path among them (`bad subject: <path> listed twice`), a sha256 that is not lowercase hex (`bad subject: "<x>" is not a sha256`), the same base, patch and files as the current subject (`bad subject: unchanged`), or a different subject once a run subject of a non-retracted Result holds the current one (`bad subject: H-…'s subject ran in R-…; a different subject is a new Hypothesis: add it and supersede H-…`).
27. A `result.record` that holds both `subjects` and `fingerprints` (`bad subjects: a Result keeps subjects or fingerprints, not both`); a `fingerprints` entry that is not a lowercase hex sha256 (`bad fingerprints: …`), a list not sorted and unique (`bad fingerprints: not sorted and unique`), or more than 2000 entries (`over limit`); `subjects` with no `evidence` (`bad subjects: a Result with no evidence has no run to keep a subject of`), more than 100 `subjects` (`over limit`), a subject with no base, no patch and no files (`bad subjects: a subject with no base, no patch and no files`), a base that is not a full commit id (`bad subjects: base "<x>" is not a full commit id`), a patch that is not a lowercase hex sha256 (`bad subjects: patch "<x>" is not a sha256`), files that are not sorted and unique lowercase hex sha256s (`bad subjects: …`), the same subject twice (`bad subjects: the same subject twice`), or more than 2000 files in all (`over limit`).
28. `rubric`, `rubric_hash` or `records` on a node that is not an Experiment (`unknown field`); a `rubric` that is neither `reading` nor `name@version` (`invalid rubric`); a bundle `rubric` with no `rubric_hash`, or a `rubric_hash` that is not lowercase hex or comes without a bundle (`bad rubric: …`); both `rubric` and `decided_by`; or a `records` entry with a path outside 1–300 runes or named twice (`bad records: <path> named twice`), or a sha256 that is not lowercase hex (`bad records: …`), or more than 500 (`over limit`).
29. `reaffirm` of a node that is not live (`bad reaffirm: <id> is not live`): a superseded or abandoned Hypothesis, or a withdrawn DQ. `dq.defer` of a withdrawn DQ (`bad defer: <id> is withdrawn; resume it first`). Each would change nothing a status reads; the move applies again once the node is live.

30. An `answer` that holds a runner field, `summary`, `refers`, `role`, `closes`, `revises` or `lines`, or has a `node` or a `why` (`bad answer: owner and runner fields never mix in one event: <field> is the runner's; …`); with no key in `answers`, `accepts` and `returns` (`bad answer: empty; an answer settles at least one key`); an item text outside 1–600 runes; more than 10 items in a field (`over limit`); a key named twice in `answers` (`bad answers: <key> is named twice`), or a limit key there (`bad answers: <key> is a limit; an owner accepts or returns a limit`). A `checkpoint` that holds `refers` with `role`, `closes`, `revises`, `accepts`, `returns` or `lines` (`bad checkpoint: owner and runner fields never mix in one event: refers is the runner's and <field> the owner's; the owner's acts are an answer`), or that holds neither a non-blank `summary` nor `refers` nor an owner field (`bad checkpoint: empty; a checkpoint holds a summary, refers, or both`). An old owner checkpoint is checked as written: its `summary` is 1–600 runes. A refer's text, when it has one, is 1–600 runes (ADR 0020). A refer with no text in a checkpoint with a blank `summary` (`bad refers: <key> has no reason; a refer says why no test within the Goal's lines can settle it, in its text or the summary`).
31. `lines` on a `node.add` that is not a Goal (`unknown field: lines are for a Goal only`); more than 10 lines or 10 cites on a line (`over limit`); a line outside 1–600 runes; a cite named twice on a line; or a cite not settled when the line is written (`bad cite: line <n> cites <key>, which is not settled: <why>; a cite is a line, an accepted or closed limit, an answered reading, or a selected or contradicted Hypothesis`): a key that names no line, limit or reading, an open limit that no Result closes and no answer accepts, an open reading, a Hypothesis that is neither the current select of its question nor contradicted by a non-retracted Result, or a node of another kind. Each test reads stored facts only. A later change in the cited key's state rejects nothing (§4 lines).
32. A move whose key leads to another Goal (`bad <field>: <key> leads to G-…, not G-…; a move never crosses Goals, and a later Goal takes a case over by citing it`): a `checkpoint` `refers` key whose Goal is not the checkpoint's `node` (`bad refers`); an Experiment `aims` key of a limit or a line whose Goal is not the Experiment's (`bad aims`); an Experiment `aims` key of a reading whose Goal is not the Experiment's (`bad applies`: an Experiment applies only a reading it aims at, so the apply rule is checked where the reading enters the Experiment); a `result.record` `closes` key whose Goal is not its Experiment's (`bad closes`). A line's Goal is the Goal it is keyed on; a limit's or a reading's Goal is the one its Result's parents lead to. An answer's `answers`, `accepts` and `returns` may name keys of several Goals, and a cite (rule 31) and a reading's `of` (rule 25) may name another Goal's key: they move nothing (ADR 0020).

CLI error text is `refused: <reason>` on stderr, with exit code 1. A help request (`-h` or `--help` on any command, and `help` at the top level and on a group command) prints usage on stdout and exits 0 at every level, while a missing or unknown subcommand exits 2.

### 5.1 Write-time refusals

More refusals come from the CLI before it appends, not from `Validate`. They read derived status, recipe, rubric and record files, or the command line; `Validate` checks stored events only, so that a later change to a derivation, a recipe or a text rule cannot turn an old log into rejections. Replay accepts these events, so a log merged from another worktree can hold them.

- `hyp add exp` under Hypothesis H is refused when H's question has live rivals of H (§7.1) and `targets` names none of them, unless `--target none` is passed. Such an Experiment in a merged log still shows as `one-rival` in `hyp signals`.
- `hyp select Q H` is admitted only when the ledger (§8.1) owes it: a `select` item for H, or the owner's `choose` on Q with H a candidate. Otherwise it is refused, naming the first thing Q's turn waits on (§8.1), in this order: the first item the runner owes on Q (`Q owes the runner first: limit R-…#1`), an open reading on Q that waits for the owner (`open reading R-…#r1 waits for the owner`), a referred limit (`referred limit R-…#n waits for the owner: …`), the premise (`H-… assumes H-…, in Q-… open; decide Q-… first`), the sub-question (`awaiting_subquestions: H-… has a sub-question not answered`); or else Q's state. When a select is owed for another Hypothesis or H is not a candidate, the refusal says so. An answered Q owes no select: `hyp unselect` first, then select. The select waits on an open limit under Q whichever Hypotheses its Result judged, since its case may apply to every candidate (§8.1, ADR 0016). `hyp show Q` lists, under `not separated:`, each pair of live rivals no non-retracted Result gives different verdicts (`replay.Projection.Unseparated`); it is a derived list, not a signal, and changes nothing the ledger owes. The open-reading refusal names the reach: `open reading R-…#r1 waits for the owner; its answer can move H-…`. `hyp select Q` with no Hypothesis prints what the same ledger reads: `suggested: H-…` for an owed select, `trade-off: owner decides between …` for an owed choice, or `suggested: none (…)` with the refusal's reason. `replay.Projection.AdmitSelect` holds the rule. Replay still applies a select in a merged log.
- `hyp confirm` is retired (ADR 0019): it exits 2 before anything else, whatever its flags, naming what replaces a scope change: the runner refers the Goal line the answer will not meet and the owner accepts it, and a Goal that needs more is a new tree. `hyp select --scope-change` exits 2 with the same text. Replay still reads an old confirm (§4).
- `hyp add exp` under a Hypothesis is refused when the Experiment has no rubric: `--rubric REF` pins a bundle, `--rubric reading` says the body decides its verdicts by reading. `hyp add exp` is refused, at exit 1, when its `--recipe` is a bundle whose known answers expect a `verdict:` line (`a recipe measures and never prints a verdict; put the rule in a rubric`), when its `--rubric` names a bundle with a step section or not exactly one Standalone command, or a bundle with no known-answer case, or one where a label its cases print has no case printing `supports` or none printing `contradicts`, when `--rubric` names a bundle, the recipe is `none` and no `--records` is given (`the rubric has no measures to read: pin a recipe or --records`), and when `--rubric` or `--target` is given under a DesignQuestion (exit 2). `--records PATH` (repeatable) is read at add: a directory stands for each regular file under it, a path outside `.tree/evidence/` is refused (exit 2), and hyp stores each file's path and sha256; the new Experiment has no run yet, so every file it names is an earlier record. `--decided-by reading` is the older spelling of `--rubric reading` and writes `rubric: reading`. Replay does not check the rubric's presence: an Experiment without one in a merged log, or written before #106, still applies, and its Results record as before.
- `hyp record` is refused, at exit 1, when an `--evidence` pointer names a file under `.tree/evidence/` that is neither in its Experiment's own run nor among its `records` (`bad evidence: <pointer> is a record outside E-…'s run and its pinned records; pin it with --records on a new Experiment`), and when a file of its `records` no longer hashes as pinned (`bad records: <path> changed since E-… pinned it`). It is refused, like a recipe, when the Experiment's rubric bundle no longer loads or no longer hashes as `rubric_hash`. A Result under an Experiment with no targets records with no `--verdict`.
- `hyp record` under an Experiment whose recipe is not `none` is refused when that recipe no longer loads or no longer hashes as the Experiment's `recipe_hash`, or when an `--evidence` pointer into that recipe hashed differently from `recipe_hash` while recording (§7.6).
- `hyp record` under an Experiment that is `superseded` or `withdrawn` (§7.6) is refused, naming its replacement or saying it is withdrawn. Replay does not repeat the check: in a merged log such a Result still applies, the Experiment reads `run`, and `hyp check` warns `<E> is superseded|withdrawn but reads run`.
- `hyp add goal` is refused, at exit 1, when a `--line` names a run of 8 to 63 hex digits followed by `…` or `...` (`line <n> names a hash cut to <k> hex digits (…); a line never changes, so name the file by its whole sha256 (64 hex digits)`). The same line with all 64 digits is accepted. Replay does not repeat the check, so an old log with such a line still replays.
- Every write command is refused when its `--why`, `--body`, `--observation`, `--summary` or any `--limit` cites an id that is no node of the store. A cite is a token that starts at a word boundary with `G-`, `Q-`, `H-`, `E-` or `R-` and goes on with six upper-case Crockford base32 characters that end the word (a display id, §2), or with a placeholder mark: `<`, `{`, `…`, `...` or three or more `X`, as in `R-<new>`. A display id that resolves (§2) passes; a placeholder never does. Lower-case prose such as `E-mail` or `R-squared` is no cite, and a token right after `:` cites another store (`containment:R-ABC123`) and is not checked. The refusal names each flag and token, `--why names R-<new>, which is no node here`, appends nothing and exits 2, as `unknown node` does (§2). Text written before this rule, or by an older binary, replays unchanged.

`hyp add exp` also warns, without refusing, when its parent or a target is not a live rival (§7.1): it writes the Experiment, exits 0 and prints one `warn: D1:` line per such Hypothesis with its status, the Results that contradict it or the Hypotheses that supersede it. It reads the same rule as the D1 signal, so the warning and D1 name the same Hypotheses.

## 6. Merge order

- Read every `.tree/events/*.jsonl` file and order all events by `id`, then by actor (the file name without `.jsonl`), whatever the line order inside a file; two lines with the same id in one file are ordered by their line bytes, trimmed, so not by file order either, and the store cut breaks a tie the same way, then by the line as written. A file that git merged with the union driver (§1) may hold two branches' lines in any order, so a store whose files hold the same lines in another order replays, prints `hyp status` and `hyp check`, and cuts the same (ADR 0022). ULIDs embed time, and §2 makes an appended id the greatest, so this is append order within one store.
- `hyp check` warns, without rejecting, when an event references an id that sorts after it.
- `hyp sandbox create --store SRC --cut EVENT` writes a store cut in this order: the merged events up to and including the first with id `EVENT` (the `asOf` stop in §7), each line as written and each events file's kept lines in id order, so the cut store replays to the same state as `asOf = EVENT` on SRC and the same lines in another file order cut to the same bytes. The cut replaces any `.tree` the base holds at its root.
- A line that does not parse has no id, so it is not in the merge. `hyp check` reports it as an error naming `file:line`; `hyp status` (with or without `--as-of`) replays the other lines, exits as usual, and prints `warn: skipped file:line: …` on stderr for each such line; `hyp sandbox create --store SRC --cut EVENT` refuses the store with exit 3, naming the first such `file:line`.

## 7. Derived state (forward pass)

Replay is a pure function: `Replay(events []Event, recipeHashes map[string]string, asOf string) Projection`. It reads no files and no clock. `recipeHashes` maps each recipe ref (`name@version`) to its current hash.

For each event, in merge order:

1. `err := Validate(state, ev)`. If there is an error, append a Rejection and continue.
2. Apply the event to the stored state: nodes, live edges, results, retracted set, abandoned set, DQ selection state, confirms, amended Hypothesis bodies and the DQ hold state.
3. Run `recompute(state)`, which recomputes every derived field below from scratch.
4. If `ev` is a **basis event** (defined in §7.3), store its snapshot, then run `recompute(state)` again.
5. For every DQ that is now `answered`, set `everAnswered[dq] = true`. It is replay's working memory of the history, rebuilt from the log on every replay and never written to it, which is what lets `reopened` differ from `open`.

Stop after the event whose id equals `asOf`, when `asOf` is not empty.

### 7.1 Hypothesis status (first matching rule wins)

1. `superseded`: a live `supersedes` edge points at it.
2. `abandoned`: it has an applied `hypothesis.abandon`. An abandon of a superseded Hypothesis is refused (§5 rule 7); once the `supersedes` edge is removed, it can be abandoned.
3. Collect the verdicts for this Hypothesis from all **non-retracted** Results. No verdicts gives `proposed`. Any `contradicts` gives `contradicted`. Otherwise any `supports` gives `supported`. Otherwise it is `inconclusive`.

A Hypothesis's status reads verdicts only. A sub-question does not change it: the block it puts on its parent belongs to the question that selected the parent (§7.4).

A Hypothesis is **live** unless it is `superseded` or `abandoned`. A DQ is live unless it is withdrawn.

A Hypothesis is a **live rival** when it is live and not `contradicted`. The untargeted-rival refusal (§5.1), the one-rival and D1 signals count live rivals. Staleness (§7.3) and the candidates (§7.4) count live Hypotheses, contradicted ones included.

### 7.2 Combined status graph (for cycle refusal)

What reads what: a Hypothesis reads only other Hypotheses, its status from verdicts and its stale through `depends_on`. A DQ reads its child Hypotheses, the sub-questions of its selected one and its own `depends_on` targets. No edge runs from a Hypothesis to a DQ, and a DQ reads other DQs only down the tree, so a cycle can only run through `depends_on` between Hypotheses. A new `depends_on` that would make such a cycle is refused (§5 rule 11). Because of this, derived fields can always be computed by memoized recursion without looping.

### 7.3 Stale (snapshot rule, the minimal form of truth maintenance)

- Stale is computed only for **live** Hypotheses and live DQs. Every other node reports `stale = none`.
- **Basis events for node N:** a non-retracted `result.record` with a `supports` verdict for N (when N is a Hypothesis); `dq.select` on N (when N is a DQ); `reaffirm` on N; and `edge.add depends_on` whose `from` is N.
- **Snapshot:** after a basis event for N, for each live `depends_on` target T of N, store `snap[N][eventID][T] = (T.status, T.stale != none)`.
- **Effective snapshot for edge N→T:** take the latest basis event of N, in merge order, that is still in force and whose snapshot includes T. A `result.record` stops being in force once retracted. Retracting therefore falls back to the previous snapshot, which is what makes "retract restores the earlier statuses exactly" hold.
- **N's stale cause** comes from the first target T, in edge-add order, that meets one of these:
  - `T.status != supported` gives cause `{Node: T, Reason: T.status}`;
  - `T.stale != none` gives cause `{Node: T, Reason: "stale", Next: T.staleCause}`;
  - an effective snapshot exists and is not `(supported, false)` gives cause `{Node: T, Reason: "changed_since_basis"}`.
- If nothing matches, stale is `none`.
- `reaffirm` creates a new snapshot. On a node that is not live it is refused (§5 rule 29), since such a node has no stale. It cannot clear staleness while T is still unsupported, because the first test is always live; `hyp check` warns "reaffirm had no effect" in that case.
- `depends_on` is never followed across `supersedes`. A superseded target is not `supported`, so its dependents go stale until the agent re-points the edge and reaffirms.
- A sub-question on a target does not make its dependents stale, because it does not change the target's status. A claim that rests on an answer says so with `depends_on`.
- Stale is returned as a cause chain, not a bool, so the status screen can print `H-5 stale ← H-3 contradicted ← R-9`. The chain ends at the Result that contradicted (the latest non-retracted contradicting Result), when there is one.

### 7.4 DesignQuestion state

Hold state is the latest of `dq.defer` / `dq.withdraw` / `dq.resume`; resume clears it. The latest in merge order wins: a withdraw is undone by a resume, and a resume of a DQ with no hold changes nothing. A defer of a withdrawn DQ is refused (§5 rule 29): the question no longer matters, so parking it says nothing; a resume brings it back first. A withdraw of a deferred DQ applies and replaces the defer. Events under a held DQ still apply: a select, an unselect, a new child Hypothesis, an Experiment and a Result are kept, the DQ reads `deferred` or `withdrawn` and its turn is closed (§8.1), and a resume derives its state from all of them.

One record, the question's `Decision`, owns everything below except the hold state: select history (each select with the candidates when it applied), conflicts, the limits under the question (§8) and the reason order. Render, signals, check and the CLI read it.

Selection is the current selection id (`""` when there is none) plus a conflict set:
- Applying `dq.select` or `dq.unselect` whose `prev_select` ≠ the current selection id adds both ids to the conflict set. The event still applies; the last one in merge order becomes current.
- A later select or unselect whose `prev_select` equals the current id clears the conflict set.
- **Candidates at the select**: when a `dq.select` applies, replay stores the question's candidates just before it, as it stores the live rivals at an Experiment's add (§8). It is a fact derived at apply time, not a payload field, so old logs get it too.
- A **candidate** is a live child Hypothesis whose status is `supported`; neither stale nor an open sub-question removes it. Two or more candidates are a **trade-off**, a state derived from the candidates and never recorded; an older select's stored `tradeoff` is ignored. The owner ends a trade-off with their choice, recorded as the select (ADR 0015): hyp admits that select only when the ledger owes the choice (§5.1, §8.1). The select holds what was chosen, not who chose it: its actor is whoever wrote it, and no status reads its `why`.

The state is decided by the first matching rule:
1. `withdrawn`, then `deferred` (from the hold state).
2. `answered` when all of these hold: the conflict set is empty; there is a current selection, naming a live child Hypothesis that is `supported` and not stale; the selected Hypothesis has no **open sub-question**, meaning one that is not withdrawn and not `answered`, so a deferred one still blocks; the DQ itself is not stale; and every candidate now was a candidate when the current select applied (a candidate that fell since does not count). An old select's `scope_change` changes nothing (ADR 0019).
3. Otherwise the state is `reopened` if `everAnswered`, else `open`. (A DQ that its own derivation reaches again reads `open` with no reason; §7.2's cycle refusal makes that unreachable, and it is only a guard against looping.) The reason is the first that holds:
   `conflicting_selections`, `selected_not_supported`, `selected_stale` (selected Hypothesis or the DQ is stale), `awaiting_subquestions` (the selected Hypothesis has an open sub-question), `new_candidate` (a candidate now was not one when the current select applied, such as a rival whose only `contradicts` was retracted), `no_candidates` (no live child Hypothesis), `untested` (every live child is `proposed`), `all_contradicted` (every live child is `contradicted`), `inconclusive` (no live child is `supported`), `supported_unselected`.

A change that adds no candidate, such as a retract that leaves the selected Hypothesis supported, a new rival or an amend, leaves the question answered: the select is the gate, and the ledger owes what such a change brings (§8.1). The verifier-loop signal and its chain were removed with the verifier role (ADR 0015).

**Status mark:** the owner's `choose:` line under AWAITING OWNER (§8.1) ends `(no Result separates them)` unless a non-retracted Result supports one candidate and gives another candidate a different verdict. The mark is derived at render and changes no state.

**Suggestion:** `hyp select Q` with no Hypothesis reads the ledger, as admission does (§5.1): it suggests the Hypothesis of an owed `select`, prints "trade-off: owner decides between …" for an owed `choose`, and otherwise prints `suggested: none (…)` with the reason a select would be refused, such as `awaiting_subquestions: H-… has a sub-question not answered`.

### 7.5 Goal

- `complete` when the Goal has at least one live DQ as a child and every live DQ whose parent is the Goal is `answered`; a Goal with no live top-level DQ is `in_progress`, because nothing has been asked yet. It reads no line: a line of the Goal is owed on each top-level question as a `limit` item (§8.1) and the select waits on it, and the owner's "met" is a complete Goal with no line under OWED. hyp stores no word for it. Sub-questions are covered through the `answered` rule of §7.4, so sub-questions under rejected rival hypotheses never block the Goal. (This clarifies the advice's "nothing stale" clause: stale on the selected path already prevents `answered`.)
- Otherwise `in_progress`, with counts per DQ state over all DQs and a count of stale live nodes.
- **Constraints block.** A Goal body's constraints block runs from the first line that starts with `May change:`, `Read only:` or `Never:` to the end of the body. It is valid when it holds each of the three headings and every non-empty line in it starts with one of them. Replay stores no word for it and no status reads it. `hyp add goal` admits any body and warns when the body has a heading but no valid block. `hyp prompt G --actor A` prints the `/goal` prompt for G from G's node and the store's place in its repository: the store's path relative to the repository root, A, G, the skill hyp-goal-run, the stop clauses, and each block line as written, in body order; `--branch` and `--pr` add a clause each after the block. It refuses with exit 1 and nothing on stdout when the block is missing or not valid, naming each problem, and exits 2 with no `--actor` (it does not read `$HYP_ACTOR`), for an id that is not a Goal, or for a `--branch` that holds a space or a control character. It exits 3 when the store's directory cannot be resolved or no repository holds its real directory, so a store whose real directory is outside every repository exits 3 even when a link inside a repository reaches it. It checks the block first, so a Goal with no valid block exits 1 wherever the store is. Lines split on `\n`, and a line is empty only when it holds no byte, so a line of spaces, a tab, or the lone `\r` of a blank line in a CRLF body is a bad line inside the block. The store's path is read after resolving symbolic links, so a store reached through a linked directory prints the same bytes. Each block line prints as written, so a CRLF body with no blank line in its block keeps the `\r` at the end of each block line. It reads no answer, so the same Goal and flags print the same bytes before and after an answer and in a store with other Goals.

### 7.6 Experiments and Results

- An Experiment's status, first matching rule wins (ADR 0008):
  1. `run`: it has a non-retracted Result. A live Result beats a close.
  2. `superseded`: a live `supersedes` edge from another Experiment points at it.
  3. `withdrawn`: it has an applied `experiment.withdraw`.
  4. `planned`.

  `superseded` and `withdrawn` are **closed**. Removing the `supersedes` edge reopens an Experiment. A closed Experiment keeps its D1 and one-rival marks in `hyp signals`; `hyp status` lists no line for it, and `hyp show` prints `status: superseded (replaced by E-…)` or `status: withdrawn`. Question and Goal states do not read Experiment status, so a close changes neither.
- A **pin** is a recipe ref (`name@version`) and the hash an event recorded for it at write time. A bundle is its ref and hash; a `recipes/<name>@<version>/` directory name is only the library's lookup key, and hyp opens each copy it makes by the ref it holds ([ADR 0005](adr/0005-a-bundle-is-its-ref-and-hash.md)). A Result depends on its Experiment's pin (`recipe` and `recipe_hash`, unless the recipe is `none`), on its Experiment's rubric pin (`rubric` and `rubric_hash`, when it names a bundle), and on one pin per entry of its own `evidence_hashes`, whose ref is the pointer's first segment under `recipes/` after cleaning the path. A Result is `questionable_evidence` when, for any pin it depends on, `recipeHashes[ref]` is missing or differs from the pinned hash. A new version of a recipe is a new ref, so it never flags Results recorded under an older one. `recipeHashes` leaves out a bundle that cannot be hashed (a symlink, a file or directory name outside `[A-Za-z0-9._-]`, or a `recipe.md` whose name or version does not match its directory; a name below a known answer's `known-answers/NAME/input/` may also hold `@`, so an input can hold a store with its pinned bundles) and a ref whose copies hash differently, and `hyp check` names each one. A bundle that hashes but does not open stays in `recipeHashes`, so its pins verify, and `hyp check` names it too (sandbox spec §1.2). This is a flag only and never changes any status.
- **[added]** An evidence pin records the bundle as it was when the Result was written, not when its files were read; an edit made in between and undone before recording is not detected, and for refs other than the Experiment's own, neither is one still in place. `hyp record` refuses a Result whose Experiment's recipe no longer hashes as the Experiment pinned, or whose evidence pin for that recipe differs from the Experiment's `recipe_hash`, so a Result never pins two hashes for one ref. Replay does not repeat that check: such an event still applies and reads as questionable.
- **[added]** A matching hash says the procedure is the same, not that it gives the right answer. An **instrument** is a recipe bundle with an Evidence or Standalone command, the checks a verdict counts. A script whose output a Result's verdict counts lives in a bundle and runs as one of its commands (sandbox spec §1), never outside `recipes/`. An instrument must have known answers: cases under `known-answers/NAME/`, each an `input/` and an `expect.json` (`RECIPE-FORMAT.md`, Known answers). A frozen recipe whose cases print `verdict: LABEL=WORD` lines is checked as a rubric is, and `hyp bundle check` warns when a label has no case printing `supports` or none printing `contradicts`, on a malformed verdict line and on a label printed twice in one case (ADR 0004); for a rubric it prints what `hyp add exp --rubric` refuses. Before every `hyp sandbox create` (for each stacked recipe, in stack order, before anything is made), `hyp bundle run` and `hyp bundle evidence`, hyp runs the instrument's known answers with the operator's hyp; a failed case refuses the run with exit 1, a timed-out case exits 3, and a refused create leaves no sandbox. `hyp add exp --recipe` refuses an instrument with no case. An Experiment under a Hypothesis declares how its verdicts are decided with its rubric, a bundle or `reading` (§5.1, next bullet). Replay never reads the declaration, and a false `--rubric reading` that hides a measure is not seen. The sandbox record and the command record both hold the outcome of each case, as `known_answers` (sandbox spec §5.1). A bundle without an Evidence or Standalone command is not gated (ADR 0002).
- **[added]** Recipe and rubric (ADR 0018). A recipe's checks print **measures**, never a verdict: one named line about one subject, such as `S1 fail` or `stored rows 4`. A **rubric** turns measures into verdicts: a bundle under `rubrics/` with no step section and one Standalone command, which reads the records it is given and prints one `verdict: LABEL=WORD` line per label. Each label its cases print needs a case printing `supports` and a case printing `contradicts`, which `hyp add exp --rubric` requires (§5.1), and its known answers gate every run, as a recipe's do. hyp never binds a label to a target and never reads a verdict line at run time: the runner types each target's verdict into `hyp record` (ADR 0004). An Experiment's rubric replaces `decided_by` and the older instrument test: an Experiment with targets declares a rubric, a bundle or `reading`, and one with no targets has none. A frozen recipe whose checks print verdicts stays history: Experiments that already pin it record as before, and no new Experiment pins it.
- **[added]** A Result is **uncontained** when hyp cannot vouch for its verdict script (ADR 0002). Each reason is reported once, in this order:
  1. it cites a script outside a versioned bundle (`recipes/<name>@<version>/`): a regular file that ends in `.py` or `.sh`, has any execute bit, starts with `#!`, or ends in `.go`, `.js`, `.ts`, `.rb`, `.pl` or `.rs`, including one under `recipes/` in no versioned bundle, which hyp neither pins nor runs, and one inside a bundle that its hash skips (a dot-entry or `__pycache__`), which no pin covers;
  2. it has a pin (its Experiment's recipe, its Experiment's rubric, or an evidence pin) to a bundle with an Evidence or Standalone command, and cites no `command.json` that names that ref at that hash, records at least one command, every one of which exited 0, and holds `known_answers` with at least one case, every one `ok`;
  3. it cites a `command.json` that hyp cannot read, or that names no ref or hash, or whose ref and hash match none of its pins.

  A `command.json` among its Experiment's `records` counts as cited for reason 2, so a Result that reassesses from kept records is contained by the records it pinned. Reason 3 reads only the records the Result cites itself.

  A pin to a bundle without an Evidence or Standalone command, such as a known-answer fixture, is held by its hash alone (§7.3). The CLI derives the mark from files when it reads, as it does `recipeHashes`. Replay never reads files, and the mark never changes a status. `hyp record` warns, and `hyp show`, `hyp status`, `hyp render` and `hyp check` show it. Nothing is refused. Limits: a script named only in prose, whose output a Result cites, is not seen; neither is a hand-made output file cited beside a real command record, or a script with none of the marks in reason 1. A hand-written `command.json` that claims a clean run with passing known answers satisfies reason 2; a reviewer checks the record's `command.log` and `known-answers.log`. A script that only a Launch, Doctor, Drive or Cleanup command reaches, cited from another Experiment, is held by its hash alone: hyp runs it in a sandbox, but no reason ties that sandbox's record to the Result. The gate proves that a bundle reproduces its own expected outputs, not that those outputs are right: a weak or wrong case needs review (ADR 0002). A case and a run get the same environment, working directory and hyp, and a case compares exit code, stdout and the tree under `$HYP_OUT` (ADR 0003), so a passed gate carries over to the run, except for what a case cannot see: a read of a fixed absolute path, a read from the network, the versions of the tools on the host `PATH` after hyp, and a write outside `$HYP_OUT`; all pass the double run. The paths of a run's ARGS are the subject's, and a limit of the host, such as the length of a Unix socket path, can differ between machines. Reason 2 names why a cited record of the pin is not clean: the first failed command, or known answers that did not pass.
- **[added]** A Result's text can disagree with the files it cites. The CLI reads each local file the Result cites (a URL is skipped), up to 16 MiB each, and warns in two cases:
  1. **verdict mismatch**: a cited file holds `verdict: LABEL=WORD` lines (WORD is `supports`, `contradicts` or `inconclusive`) for a Hypothesis the Result judges, LABEL being its alias, display id or id, and none of them gives the verdict the Result typed;
  2. **uncited**: the observation or a limit holds a lowercase hex token of 7 to 64 characters, with at least one digit and one letter (a commit or a hash), that no cited file holds; the warning names the field. A reading quotes the owner and is not read. A Result that cites no readable local file gets no such warning.

  `hyp record` warns after the event is appended and `hyp check` warns per Result. Nothing is refused and no status changes; hyp never reads a rubric's prose (ADR 0004), and replay never reads files. Limits: a verdict line that names no Hypothesis is ignored, a cited file that gives two words for one Hypothesis agrees with either, an id-like word that is not hex is not seen, and a token that a cited file holds by chance passes.

## 8. Projection (what replay returns)

    Applied    []Event              // events that applied, in merge order

    Exps       map[string]*Exp       // Experiment id → its derived record, built once per projection
    Results    map[string]*Res       // Result id → its derived record, built once per projection
    Edges      []Edge                // every edge in apply order; Live is false once removed
    Decisions  map[string]*Decision  // DQ id → its Decision record (§7.4)
    Lines      []Limit               // every Goal's lines, Goal by Goal in creation order, then in order (§8.2); Result is the line's Goal id and Question is ""

type Decision struct {
    Current   string                 // the current select id, or ""

    Selects   map[string]SelectRec   // select id → its record

}
type SelectRec struct {
    ID, Hyp, Actor, Why string
    Candidates          []string     // the question's candidates just before the select applied (§7.4)
}

    // Closed()  status superseded or withdrawn: a live Result beats a close (§7.6), so the ledger and the display read this, never Close

    Status       ResStatus // recorded or retracted
    Questionable bool     // questionable_evidence (§7.6)
    Pins         []Pin    // its Experiment's recipe pin and rubric pin, then one per evidence_hashes entry, in the order cited (§7.6)
    Uncontained  []string // reasons (§7.6); set by the CLI from files, not by replay

    Key, Result, Text string   // Key is "<result-id>#<n>", or "<goal-id>#<n>" for a line; full ULID

    Status HypStatus   // §7.1
    Stale  *StaleCause // nil when not stale
}

    State      QuestionState // §7.4
    Reason     string        // open/reopened reason; "" otherwise

A confirm in an old log is in `Applied`, so `hyp status` RECENT and `hyp show` history still list it; no record keeps it, and only an owner confirm's `accepts` reaches the move table (§8.2, ADR 0019).

Limits **[added]**: a Result's limits are filed under its question, the parent DQ of its Experiment's Hypothesis, whichever Hypotheses it judged. Limits of a retracted Result are left out. A limit has two facts, and no stored word joins them: its hand, which the move table stores and reads (§8.2), and its closers, derived from Results' `closes`. Its state, as `hyp show` prints it, is:
- `closed` when a non-retracted Result lists its key in `closes`; `Closers` lists them in creation order. Retracting that Result reopens the limit unless another one closes it. `hyp show` prints each closer with its verdicts (`closed by R-… (H-… (alias) contradicts)`), so the line says what the case did to each Hypothesis it judged: a contradicted one failed the case. `hyp show <R-id>#<n>` prints one limit: its text, Result and question, its state and, while open, whose turn it is; each Hypothesis its Result judged with its status now; the question's candidates; for a closed limit, each candidate no closer judged (`not judged by a closer:`); the Experiments that aim at it; and a history of the Result that records it, the Results that close it with their verdicts, and the checkpoints and confirms that refer, return or accept it with their summaries. A key that names no limit of a live Result is exit 2.
- otherwise `accepted` when its latest hand (§8.2) is an accept, by that accept's actor. A Result that closes it comes first. An old owner confirm's `accepts` is an accept at the confirm's place in the log, and a return lifts it like any accept.
- otherwise `open`. An open limit whose key a checkpoint lists in `refers` is **referred**: the runner says no test within the Goal can close it, or that its case is void for every candidate, and only the owner can settle it: by accepting it, so this tree does not run the case, or by returning it (`returns`), because the Goal covers its case. The latest `refers` or `returns` in merge order names whose turn an open limit is: a returned limit is the runner's again, owed, with the select waiting on it like any open limit, until a Result closes it or a later checkpoint refers it again. The select and the choice on its question wait on a referred limit too, because a return sends its case back to run and its Result can change the candidates: `hyp select` refuses with `referred limit R-…#n waits for the owner: an accept releases the select, a return sends its case to run`. New rivals do not wait on it. A return also reopens a limit an owner checkpoint accepted, so an owner who changes their mind writes one checkpoint: the latest of accept and return stands. A limit's category is never stored (ADR 0016): a close with the closer's verdicts, an accept, and the latest refer or return are what it is.

Lines **[added]**: a line of the Goal (§4 lines) is a limit with the Goal for its Result. It has a hand and closers as a limit does, and is neither open nor closed: whether its case ran is per candidate, its coverage. `Open()` of a line means only that its hand is not an accept. **Coverage**: a Result covers a Hypothesis when it has a verdict on it, or when one of the Result's run subjects holds the Hypothesis's whole subject (§4 subject; `Projection.Covers`). Coverage says the bytes ran, not that the claim held. A line is **covered** on a question when a closer of the line covers each of its candidates, and **uncovered** there otherwise. An unaccepted, unreferred line is owed on each live top-level question where it is uncovered (`Projection.Uncovered`), so a new candidate is owed the line again. Coverage is not a state of the move table: it changes when a candidate is added or falls, with no move on the key, and no move reads it. `hyp show G-…#n` prints the line's text, its hand when it has one (`hand: accepted by o`), each cite with what it meant and, when that differs, what it would mean now (`cites H-…: realised, now unsettled`), each top-level question's candidates with `covered` or `uncovered: H-…`, each closer with what it ran on (`ran in R-…: ran on H-… (alias): supports; ran on H-…`), the aiming Experiments and the history. A verdict is per Hypothesis, never per line: a Result that closes several lines and contradicts H says the cases ran and H failed, not which line, so nothing prints `fails <line>`. `hyp status` prints a LINES section under the GOAL line, one line each with its facts joined by `; `, each only when it has one: its hand, `covered on Q-…, Q-…` and `uncovered on Q-…: H-…` for each live top-level question with a candidate, and `ran in R-…`; a line with none prints `no candidate`. Neither `open` nor `closed` prints for a line. The section also prints and the mark `(no one closer covers H-… and H-… together)` when the Hypotheses selected on two or more top-level questions were never covered by one closer (`Projection.NotTogether`); a claim that depends on its host is covered only together with it. No item and no status reads the mark. `hyp show <Goal>` lists the lines, and `hyp show <H>` prints a tied subject.

Limits never change a derived status. Only the CLI and the ledger read them: `hyp show` and `hyp status` list them, and the select of a question with a candidate waits on an open limit under it through the ledger (§8.1), whichever Hypotheses its Result judged.

### 8.1 Ledger: what the tree owes

`Projection.Owed()` derives the ledger: each item of open work on a question, with who owes it. An open or reopened question owes every kind of item; an answered one owes only the `limit`, `reading`, `referred` and `premise` items, so evidence that lands after the answer is owed and not only listed. Nothing stores the ledger, and owing an item never changes a status: the gate is at the write (§5.1), not in the derivation. Settling one is always an explicit event; a planned test is intent, not an outcome, so an Experiment's `aims` never settles a limit or a reading, and settling an item never selects, answers a question or meets the Goal. OWED is per Goal: an item belongs to the Goal its question's parents lead to, a line is owed only on the top-level questions of its own Goal, and coverage of a line reads only those questions' candidates. `hyp status G-…` prints one Goal: its GOAL, LINES, FRONTIER, STALE and OWED, then AWAITING OWNER, OPEN LIMITS, RECENT, CHECKPOINT, QUESTIONABLE and UNCONTAINED, each reading only that Goal's items, so each equals what the Goal's own events give in a store of their own; REJECTED counts the store's rejections. An event belongs to a Goal when its node leads to it, or, for an answer, which is on no node, when one of its keys does. CHECKPOINT is the Goal's latest runner checkpoint (`LastCheckpoint`); an old owner checkpoint is history and not one. `hyp status` with no Goal prints that view of the one Goal in a one-Goal store, as it always did. In a store with many Goals it prints a GOALS table, one row per Goal in creation order with its state and counts, `runner owes N` or `runner owes nothing`, and its last checkpoint; then one AWAITING OWNER list, grouped by Goal, each Goal with an item under its own heading; then REJECTED. Items, per question in creation order:

| Item | Who | Owed while | Settled by |
|---|---|---|---|
| `rivals` | runner | the question has no live, non-contradicted Hypothesis and no open reading on its Results with a reach (§4 readings); `hyp status` names each contradicted Hypothesis and the Results that contradict it (`ruled out: h-one by R-…`) | a new Hypothesis |
| `untested` | runner | a proposed Hypothesis has no planned or run Experiment as parent or target | an Experiment |
| `undecided` | runner | a live Hypothesis is `inconclusive` (neither supported nor contradicted) and no planned Experiment has it as parent or target | a planned Experiment, then its Result |
| `planned` | runner | an Experiment is planned, under a Hypothesis of the question or, with no targets, under the question itself | its Result |
| `limit` | runner | an open limit under a question that has a candidate, whichever Hypotheses its Result judged, unless its latest hand is a refer; or, on a live top-level question, an open line of its Goal that is not referred and that a candidate has no closer covering | a Result that `closes` it (for a line, one that covers each candidate), or a `refers` |
| `referred` | owner | an open limit's latest hand is a refer, whichever Hypotheses its Result judged; a referred line is owed on each live top-level question; `hyp status` prints `limit referred, accept or return` | an owner checkpoint that `accepts` or `returns` it |
| `reading` | runner | the answer in force of a closed reading is not applied, including after a revision | a Result that `applies` it |
| `premise` | runner | a candidate's live `depends_on` target T sits under another question whose current select names a Hypothesis other than T | re-pointing the edge (`hyp unlink`, `hyp link`), superseding the dependent, or that question selecting T |
| `stale` | runner | the question reopened `selected_stale`, owes no other runner item and does not wait on a premise; the key is the selected Hypothesis when it is stale, otherwise the question | a `reaffirm` of the key, or a new basis that clears the stale cause (§7.3) |
| `select` | runner | the question's turn is `owed` (below) and it has one candidate | `dq.select` |
| `choose` | owner | the question's turn is `owed` and it has two or more candidates | `dq.select` of a candidate, with the owner's words in `why` |

**Turn.** `Projection.Turn(Q)` derives where Q's decision stands, by one rule, first match wins; nothing stores it, and the ledger, `hyp select` and `hyp status` read only it:

1. `closed`: Q is `answered`, `deferred` or `withdrawn`. A select that stands is an answered question (§7.4); there is no other standing.
2. `waits`: something must happen before a select or a choice. The turn lists every such thing, in this order: runner work (any runner item on Q, the first one named); an open reading on Q's Results with a reach (§4 readings); a referred limit under Q, or a referred line when Q is top-level; a premise (below); a sub-question not answered of the current select's Hypothesis when Q reopened `awaiting_subquestions`, or else of the lone candidate (ADR 0014). A choice between two or more candidates does not wait for sub-questions.
3. `no_candidate`: Q has no candidate. The rules above always owe the runner work on such a question, or wait on a reading, so this value is a guard.
4. `owed`: the runner's `select` of the lone candidate, or the owner's `choose`.

A reopened question that keeps its select is never owed a select of the same Hypothesis while nothing changed: `conflicting` and `new_candidate` make the turn owed again, and the new select stores the new candidate set; `selected_not_supported` leaves the selected Hypothesis no candidate; `awaiting_subquestions` waits; `selected_stale` owes `stale`, or waits on its premise. `hyp select` refuses with the first thing the turn waits on, or with Q's state.

The **premise**: Q's turn waits while a candidate has a live `depends_on` target under another question that is `open` or `reopened`; the `assumes … in Q-… open` line under the candidates in FRONTIER is its reason, and `hyp select` refuses with it. The runner settles the premise's question first. A `depends_on` target under Q itself is no premise, because the choice between them is Q's own. Two questions whose candidates assume each other's Hypotheses make each other wait; `hyp check` warns `premise cycle between Q-… and Q-…`, and removing an edge breaks it. An answered Q whose premise's question later reopens owes nothing until that question selects against the premise.

A `limit` or `reading` item also has an aim state: `owed` when no live Experiment aims at its key, `in_progress` while an aiming Experiment is planned, and `aimed_not_settled` once every aiming Experiment has a Result and none settled it. An open reading is owed by the owner too; `hyp status` prints it under AWAITING OWNER from its own record. A trade-off is a state, printed as `(trade-off)` on the question's candidates line in FRONTIER; only `choose` is the owner's turn, and it waits for the runner because every runner item can change the candidates.

`hyp status` prints the runner's items under OWED, keeping the first five when it truncates, and the owner's under AWAITING OWNER. `hyp status --live` leaves out of FRONTIER each contradicted Hypothesis that holds no open Experiment marked one-rival, and prints `(N contradicted hidden)` under its question; it is the owner's view, and the other sections are the same, since a runner needs the contradicted rivals to supersede them. A question whose turn waits on something other than runner work prints one line under it for each thing, so `runner owes nothing` names its reason: `waits on open reading R-…#r1 for the owner; its answer can move H-…`; for a question with a candidate, `waits on referred limit R-…#n for the owner; an accept releases the select, a return sends its case to run`; `waits on a sub-question of H-… not answered`. A premise has its `assumes` line instead. Under a grouped reading line, each key prints what the answer can touch on its question: `R-…#r1: Q-… candidates …` (or `no candidate`) `; judged H-… supports, now contradicted`, from the Result's verdicts and each Hypothesis's status now. When no item is the runner's, OWED ends with `runner owes nothing: stop and report to the owner`, the stop clause a run reads; an item on an answered question counts, so a run does not stop with a limit or a premise it owes there.

Rivals at add **[added]**: when an Experiment under a Hypothesis is applied, replay stores the live rivals of its parent under the same question, read from the derived state just before that event. An Experiment is **one-rival** when that list is not empty and its `targets` name none of it. The mark is read at the Experiment's add, so a rival that dies later does not clear it, and a rival added later does not create it. `hyp signals` reports it, and it never changes a derived status. The `unjudged` mark is retired: rule 6 refuses a Result that leaves a target without a verdict (ADR 0018).

The Projection holds every fact hyp derives; render, signals and the CLI read its fields, and nothing stores them a second time (ADR 0006). Scripts read the applied events and rejections through `hyp events --json` and each round's facts and design marks through `hyp signals --json`, never the files under `.tree/events`.

Each node kind has its own status word: `HypStatus`, `QuestionState`, `ExpStatus`, `ResStatus` and `GoalState` are separate string types, so comparing two kinds does not compile (ADR 0013). A `Question` reaches its `Decision` by the shared id. `Projection.Display(id)` returns the word, reason and stale cause of any node, for code that prints a node without knowing its kind. A rule that joins several words of one kind has one name, and callers read the name instead of comparing words: `QuestionState.Open` (open or reopened, the states the ledger works), `QuestionState.Obliges` (a sub-question not withdrawn and not answered, deferred included), `LiveHypStatus` and `RivalStatus` (§7.1), `Exp.Closed` (§7.6), `Reading.Open` (no checkpoint closed it), `Projection.LiveResults` (the non-retracted Results in merge order), and `HandMove` for a limit key's latest move (§8.2).

Equality test used by acceptance: every node's derived record and the Goal are deeply equal.

### 8.2 Keyed items: limits, lines and readings

A **keyed item** is created as one entry inside its parent's event and addressed as `<parent>#<n>` or `<parent>#r<n>`: a limit inside a Result, a reading inside a Result, a line inside the Goal's `node.add` (an old Goal's inside the owner checkpoint that wrote its lines), keyed on that Goal. Its text is fixed, it takes no edge, and it is gone when its Result is retracted. Only other events move its state. `internal/replay/keyed.go` holds the move tables: `Validate` asks them before a move applies, apply records the move in `Facts`, and `limits()`, `lines()` and `readings()` read only what they recorded. The states are derived; what is stored is each key's latest hand and each reading's answers.

**Limits and lines.** Stored per key: `Hand` — the latest refer, return or accept, its event and actor, and the actor of the latest refer (`Referrer`). Derived beside it, as a second fact and not a state of the table: its closers, from which §8 (Limits) derives `closed`, `accepted` and `open`; the `notRun` column reads `closed`, for a Result's limit only. A line's coverage is read per candidate (§8, Lines), and no move reads it.

| Move | Field | Admitted when the latest hand is | By | Refused also when |
|---|---|---|---|---|
| refer | checkpoint `refers` | none, a refer or a return | any actor | a Result closed the limit (a Result's limit only); the key leads to another Goal than the checkpoint's |
| accept | answer `accepts` (an old owner checkpoint's `accepts`) | a refer | an answer or an old owner checkpoint, not the latest referrer | a Result closed the limit (a Result's limit only) |
| return | answer `returns` (an old owner checkpoint's `returns`) | a refer or an accept | an answer or an old owner checkpoint, not the latest referrer | a Result closed the limit (a Result's limit only); the key is also in `refers` or `accepts` |
| close | Result `closes` | any | a Result under its question, or any Result whose Experiment aims at it; any Result for a line | the key leads to another Goal than the Result's |
| aim | Experiment `aims` | any (intent, settles nothing) | any | the key leads to another Goal than the Experiment's |
| accept (history) | owner confirm `accepts` | any; rule 17 still applies | the confirm | — |

An accept answers a refer, except the history row: an old owner confirm's `accepts` applied with no refer, and replays as it was written. A new accept needs a refer, so a waive is always two steps, the runner's refer and the owner's accept, and after a return a new accept needs a new refer. Separation of duties compares the answer with the latest refer, never with the author of the key's Result or of the Goal, so an owner answers a refer of their own line. A refer of an accepted limit is refused because only the owner reopens one, and a refer of a closed one because its case ran: no test is left to refer. A line is never closed, so a line that ran on some candidates can still be referred. A move never crosses Goals: a refer, close, aim or apply whose key leads to another Goal is refused (§5 rule 32), so an item is moved only by its own Goal's runner and by the owner, and OWED, which is per Goal, names the hand the tables store. They disagree in two named cases, each accept-able by the table and owed by nobody: a referred limit on a deferred or withdrawn question, and a referred line on a Goal with no live top-level question. Within one event the moves apply in the order refers, returns, accepts. A refer and an answer's moves are never in one event: owner and runner fields never mix (§5 rule 30), and one answer may move keys of several Goals.

**Readings.** Stored per key: the answers, the close and then each revise, in merge order. Derived: `open` with no answer, else closed with the latest answer in force, and applied as §4 readings says.

| Move | Field | Admitted when the reading is | By |
|---|---|---|---|
| close | answer `answers` (an old owner checkpoint's `closes`) | open | an answer or an old owner checkpoint, not the actor that recorded the Result |
| revise | answer `answers` (an old owner checkpoint's `revises`) | closed | an answer or an old owner checkpoint, not the actor that recorded the Result |
| apply | Result `applies` | closed, and named in its Experiment's `aims`, which refuses a reading of another Goal | any Result |

A reading has no refer, so its separation compares with the Result's author.

**Crash and merged log.** A move is one event, one line appended and synced (§3); a line a crash cut short is skipped (§6), so a crash leaves the latest hand of the last whole event. In a merged log the moves apply in merge order (§6), and a move its table refuses at its place, such as an accept that sorts before its refer, or a lines checkpoint on a Goal whose add or an earlier checkpoint carried lines, is rejected and reported; the key keeps the hand it had.
